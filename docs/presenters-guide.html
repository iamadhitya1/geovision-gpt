01 — Open with this

The pitch

Two versions — the one-breath version, and the one with substance underneath it if your guide leans in.

Ten seconds

"I built and trained my own visual question answering model for satellite images — not an existing AI model called through an API, but a model I assembled, trained on the institute's GPU cluster, and evaluated myself. And there's a working web app on top, so I can show it live."

If they lean in

"The architecture follows a published paper, LiT-4-RSVQA — a small pretrained image transformer plus BERT-Tiny for the question, fused, then classified into one of a thousand answers. It's about 8 million parameters, not billions, because that's what actually fits on a shared GPU in a semester. I reproduced the paper's design and got 75.2% average accuracy on data the model never saw. My own experiment was replacing the paper's simple fusion with cross-attention — it tied the baseline, so the richer fusion didn't measurably help. That's an honest result, and I can tell you about the first attempt, which failed for an interesting reason. I then measured a real weakness — the model was brittle outside its one training dataset — and fixed it by retraining on a second, independent dataset with augmentation: same accuracy on the original benchmark, genuine generalisation to a city it never saw, and a robustness problem (a dimmer image collapsing its accuracy) largely fixed. I also measured how much of the score is just guessing from the wording of the question: a model that never sees the image gets 70.4%, so the image adds about two points overall, and clearly more on urban-versus-rural."

Say the ten-second version first, always. Only go to the second one if they ask a follow-up — don't front-load the technical version, it reads as reciting rather than understanding.

  1. Step 01 · Late August 2026

    The original plan, and a solid backend

    • Topic set with Dr. Ashish Soni: multi-modal visual question answering on satellite and Earth-observation imagery.
    • First plan: adapt a large existing vision-language model (Qwen2.5-VL) and add a training-free verification idea (SGV — checking a model's numeric claims against spectral measurements), delivered as a ten-module web app with an approval step after each module.
    • Read the two assigned survey papers (Weng et al. 2025 on vision-language models for remote sensing; Kim et al. 2025 on VQA) to understand the field.
    • Built module 1 (accounts, roles, audit trail — Argon2id hashing, single-use refresh tokens) and module 2 (image upload that checks the file really is what it claims, geo-metadata extraction, thumbnails). Four-layer architecture enforced by an automated test; about 103 tests; two review passes found and fixed 8 real issues.

    Outcome: a real, tested backend — but no model of my own yet.

  2. Step 02 · Early September

    The guide's review, and the pivot

    • Ashish's feedback: the model is the point — understand how a VQA model works inside, train one on real data using the institute's GPU. The web app is secondary but still expected, with a live demo.
    • Decision: drop the big-model-plus-verification plan and rebuild around a small model that is trained here.
    • Chose LiT-4-RSVQA (Hackel et al. 2023): BERT-Tiny plus a small image transformer. Reasons: about 8 million parameters beat a 277-million-parameter model in the paper, fine-tuning a pretrained encoder beats training from scratch by about 13 points, and it fits a shared GPU slice.
    • Defined the project's own contribution: replace the paper's simple fusion with cross-attention, on identical data and settings, and measure whether it helps.
    • Ran a literature search (September 2026) to place the work against current systems (RS-MoE, Co-LLaVA, HSF-Net, and the larger RSVLM-QA benchmark).

    Outcome: a new plan that matches what the guide asked for, with a real experiment at its centre.

  3. Step 03 · Early September

    Data and model built — and verified without a GPU

    • Downloaded RSVQA-LR. Found a quirk in its files (every split file contains all questions, with a flag marking which belong to it) and verified the fix against the real data: exactly 57,223 train / 10,005 validation / 10,004 test = 77,232.
    • Built the pipeline: data loader; answer vocabulary from the 1,000 most common training answers only (no test leakage); BERT-Tiny (the official Google checkpoint — a community copy failed to load); XCiT-Nano (with DeiT-Tiny and MobileViT-S as alternatives); the elementwise fusion; the classifier.
    • Wrote training and evaluation scripts that run identically on CPU or GPU, and ran the whole pipeline end to end on the laptop CPU first, so scarce GPU time would not be spent finding basic bugs.

    Outcome: 8,217,896 parameters, matching the paper's 8.1 million; a pipeline proven to run.

  4. Step 04 · Early September

    Getting onto the institute's GPU cluster

    • Submitted the declaration form to the AI/ML centre's coordinator; received login details. Cluster jobs must go through the SLURM scheduler, one job per user.
    • Sorted out campus network registration so the cluster was reachable.
    • Wrote SLURM job scripts for a smoke test, training and evaluation, checked over before the first real session.
  5. Step 05 · 8 September

    First real GPU session — four problems a laptop could not show

    • Reserved GPU. Three of the four GPUs share one label; a plain "one GPU" request could land on the reserved one. Fix: request a named 1g.10gb slice of GPU 3.
    • Driver mismatch. Default PyTorch was built for a newer CUDA than the driver (12.4), so training silently ran on the CPU. Fix: install the matching build.
    • Slice addressing. The scheduler's slice identifier did not match what the GPU software needed, causing another silent CPU fallback. Fix: the job script looks up the correct identifier itself.
    • Out of memory. The paper's batch of 512 does not fit a ~10 GB slice. Fix: batch 64.

    Lesson: each was diagnosed from the cluster's own output. Two were silent — the job ran, just on the wrong device — so the logs had to be read, not just the exit status.

  6. Step 06 · 8 September

    Baseline trained and tested

    • Ten epochs, about 73 minutes on one GPU slice. Scored once, on the held-out test split (9,838 questions).

    Result: 72.74% overall, 75.16% average accuracy. By type: rural/urban 92.0%, presence 90.7%, comparison 90.4%, counting 27.5%. (The paper's 64.61% used a different, much larger dataset — not like-for-like.)

  7. Step 07 · Mid September

    Serving the model: the backend gets a brain (Module 3/4)

    • Added the question-answering service: ownership check, both models run, answers with confidence and runner-ups stored and audited. Model code shared with the training code instead of copied. Unit tests with hand-written fakes; 109 tests.
    • Found and fixed three packaging bugs by inspecting the built package, not assuming: a folder named data was silently dropped from the wheel (renamed dataset); the wheel was bundling the 150 MB dataset; the tokenizer loaded eagerly (test suite 154 s → 32 s).
    • The project report (Word) and the study material were kept in step throughout.
  8. Step 08 · 17 September

    The cross-attention experiment fails

    • The first cross-attention run finished cleanly but scored only 36.06% overall (27.07% average). Its validation accuracy sat on the same one or two values from the first epoch to the last.

    Reading: a model giving nearly the same answer whatever it is asked. Not reported as a finding — investigated.

  9. Step 09 · 21 September

    Bug found, proven, fixed — and an honest result

    • Cause: the image and question had each been reduced to a single token before attention, so attention ran over one item; softmax over one item is always 1; the question never influenced the output.
    • Proof: changing the question changed the module's output by exactly 0.0; changing the image changed it by 0.84.
    • Fix: attend over sequences — every question word over all 197 image tokens. The fusion is now chosen inside the model (three scripts had each swapped it in by hand, which is how it went unnoticed). A regression test checks that both question and image change the output.
    • Also found that the backend imported a frozen copy of the model code, so the fix would never have reached the app; made the link live.
    • Retrained (about 91 minutes) and tested.

    Result: 72.33% overall / 72.29% average — effectively tied with the baseline. Reported as "the richer fusion did not measurably help", with the caveat that each model was trained once.

  10. Step 10 · 21 September

    The full web app: frontend, map, dashboard (Modules 5–7)

    • Next.js interface: sign-in, image library with drag-and-drop upload, a workspace showing both models' answers side by side with a low-confidence warning, question history.
    • Map view of georeferenced scenes; dashboard with measured accuracy and live usage (a new statistics endpoint in the backend, with tests).
    • Checked at desktop and phone widths; fixed a header that overflowed on mobile.
    • One-command demo launcher and a demo runbook. Testing the launcher from a cold start found a real bug (a database step that failed on the app's own database); fixed.

    Outcome: a working live demo with both models loaded, about 0.4 s per question per model on a laptop CPU.

  11. Step 11 · 21 September

    Testing the result honestly

    • No-image baseline: a predictor that never sees the image (most common training answer for each exact question) scores 70.42%. So the image adds only about two points overall — clearly on rural/urban (56% → 92% / 81%), slightly on presence and comparison, not at all on counting. Now a grey bar on the dashboard.
    • Robustness study: dimming an image drops the baseline's rural/urban accuracy from 92% to 62%; halving its resolution drops it to 58%; and about 13% of answers flip under a mirror or rotation that cannot change the true answer.
    • Custom image test: PNG/JPEG uploads work, but a 2× zoomed crop flipped an urban answer to rural at 95–99% confidence.

    Conclusion: the model works on imagery like its training data and is brittle outside it. That is now a measured statement, and it set the next goal.

  12. Step 12 · 21 September

    Backup and documentation

    • All code pushed to a private GitHub repository; the trained models, answer vocabulary and report attached to a release. Restore tested with a fresh clone and matching checksums.
    • Report updated with the real results, the failed first attempt, and the no-image finding; this presenter's guide written; demo runbook in the repo.
  13. Step 13 · 22–23 September

    Widening the model so it works beyond a few selected images

    • Decision: a model useful beyond one dataset matters more than putting the demo online, so the deadline was extended.
    • Plan: retrain on RSVQA-LR and RSVQA-HR (15 cm aerial imagery, about a million questions; its second test set is an unseen city, Philadelphia), with augmentation that keeps the true answer correct.
    • Built: a resumable trainer that stops itself before the cluster's 4-hour limit and continues where it stopped (tested by interrupting and resuming); augmentation, with a rule that directional questions are never mirrored (tested); a bug caught in review before it cost a training run — data-loading workers were each replaying the same "random" augmentation sequence, fixed with a test. The original training script was left untouched so the original baseline stays reproducible.
    • Success was defined in advance: better accuracy on the unseen city, much smaller drops under the robustness changes, and no large loss on the original test set. All three held.

    Result: 72.02% overall on RSVQA-LR (essentially unchanged from the original 72.74%); 81.9% on RSVQA-HR's own test cities and 77.2%/76.5% on Philadelphia, a city never seen in any form during training — a real ~5-point generalisation gap, not a collapse. The robustness weakness measured in Step 11 is fixed: dimming an image now costs 0 points on rural/urban (was 30), and half-resolution costs 3 (was 34).

  14. Step 14 · 23–24 September

    Widening the cross-attention model too — keeping the original comparison alive

    • Why: Step 09's baseline-vs-cross-attention comparison was the project's own experiment. Widening only the elementwise model would have quietly dropped that comparison — so the same recipe was retrained with cross-attention fusion instead.
    • Same setup: RSVQA-LR + RSVQA-HR with augmentation, 8 epochs, one training job, evaluated on all three test sets, then robustness-checked with the same perturbations as Step 11.

    Result: 71.96% / 73.91% on RSVQA-LR — still tied with elementwise (72.02% / 73.65%), confirming the richer fusion still doesn't measurably help after widening. The unseen-city gap is about 6 points (80.4%→74.4%), the same size as elementwise's — so both fusion styles generalise similarly. The robustness fix holds too: rural/urban's darker-image drop shrinks from 15 points (original cross-attention model) to 3. Both widened models now run side by side in the live app.

04 — Know this cold

How it works, end to end

One picture and six plain steps. If you can draw this from memory and say each step in a sentence, you can handle most questions.

  1. The picture goes in. The 256 × 256 satellite image is resized to 224 × 224 and cut into a 14 × 14 grid of small squares (196 patches). XCiT-Nano, a small pretrained "transformer" image model, turns each patch — plus one summary of the whole image — into a list of 128 numbers: 197 lists in all.
  2. The question goes in. The question is split into word pieces and BERT-Tiny turns each piece into 128 numbers, using the surrounding words for context.
  3. Fusion — the step I experimented with. Now the model must combine what it sees with what it was asked. A (baseline): squash each side into one list of 512 numbers and multiply the two together position by position. B (mine): let every word of the question look across all 197 image lists, weight the ones that matter to that word, and pull that information in.
  4. The classifier decides. A small network turns the fused numbers into 1,000 scores, one per possible answer. Softmax converts them to probabilities that add up to 100%. The app shows the top answer, its probability (the "confidence"), and the next-best answers.
  5. How it learned. The models the app actually serves saw RSVQA-LR's 57,223 training questions mixed with a random 60,000-question sample of a second, much larger dataset (RSVQA-HR) each epoch. For each, it guessed; a "loss" measured how far the guess was from the right answer; an optimiser (AdamW) nudged all ~8–9 million numbers a little (learning rate 5e-4). That happened 64 questions at a time, 8 full passes ("epochs") over the mixed data, about 95 minutes on one GPU slice. Nothing was frozen: the pretrained image and text models were fine-tuned too, which the paper found is worth about 13 points over starting from scratch. After every epoch it was scored on a separate validation set to watch for memorising and pick the best epoch.
  6. How it was tested. On three held-out test sets it never trained on: RSVQA-LR's own 9,838 questions (for direct comparison with the original single-dataset models), RSVQA-HR's own test cities, and RSVQA-HR's Philadelphia split — a city that appears nowhere in training, the real test of generalising beyond a handful of selected images.

How the web app fits around it

  • The browser (Next.js) signs you in and uploads an image.
  • The backend (FastAPI) checks the file really is the type it claims, reads its location data, stores it with a thumbnail, and remembers who owns it.
  • When you ask a question, the backend checks you own the image, runs both models (off the main thread so the server stays responsive), saves the question and both answers in the database, and returns them. About 0.4 seconds per model on a laptop CPU.
  • The map draws images at their real coordinates; the dashboard shows the measured accuracy and your usage.
  • Inside the backend, code is in four layers — domain rules, use cases, infrastructure, API — and a test fails the build if an inner layer ever depends on an outer one.

How to read it honestly

The two are still effectively tied — the same as before widening. Overall they differ by 0.06 points, about 6 questions out of 9,838. On every category the models are within about a point of each other. Widening the training data didn't change which fusion wins; it changed how far both generalise (below).

What you can and can't claim. You can say cross-attention still did not measurably improve on elementwise fusion, at about 13% more parameters, and that this held before and after widening the training data — a more robust negative result than a single comparison would be. You can't say either fusion is better. Counting is weak for both (about 28%), consistent with it being the hardest question type for small VQA models generally.

Against the paper. The paper reports 64.61%; these models are higher, but it trained on a much larger dataset (RSVQAxBEN, ~15M examples) and these train on RSVQA-LR directly, so it isn't like-for-like. Don't claim to have beaten it.

Against the original, single-dataset models. Elementwise: 72.74% → 72.02% (−0.7 points). Cross-attention: 72.33% → 71.96% (−0.4 points). Training on a second, very different dataset cost almost nothing on the first one — see below for what it bought instead.

Widening the model: generalisation and robustness (the newest result)

The robustness study below (Step 11) found a real weakness: a model trained on one dataset, one country, one sensor is brittle outside it — dimming an image alone dropped rural/urban accuracy from 92% to 62%. Both models were retrained on RSVQA-LR and RSVQA-HR (15cm aerial imagery, ~1.07M questions, an independent dataset with its own unseen-city test split, Philadelphia) with label-preserving augmentation.

RSVQA-HR (same cities)RSVQA-HR Philadelphia (unseen city)
Elementwise — overall / average81.9% / 81.4%77.2% / 76.5%

Reading it honestly. A ~5–6 point gap between RSVQA-HR's own test cities and Philadelphia — a city that appears nowhere in training, in any form — is a real but modest generalisation cost, not a collapse to guessing. That is the actual evidence for "generalises beyond a handful of selected images," and it holds for both fusion styles, not just one.

Did it fix the robustness problem? Yes, measurably, for both models. Same perturbations, same RSVQA-LR test images, compared against each model's own original single-dataset version:

Change (rural/urban)Elementwise: original → widenedCross-attention: original → widened
Clean image92% → 88%81% → 89%
Darker (×0.6)62% → 88% (was −30 pts)66% → 86% (was −15 pts)

The darker-image drop, the clearest sign of the original brittleness, shrinks dramatically for both fusions. Half-resolution improved for elementwise but not for cross-attention — worth naming as an honest partial limit rather than claiming a complete fix on every axis.

What the image actually adds — the number to know

A predictor that never looks at the image and answers each question with the most common training answer to that exact question scores 70.42% overall — because RSVQA-LR's questions are templated. So both models beat it by only about 1.5–1.6 points overall. The image clearly matters for rural/urban (56% → 88% and 89%), adds a little on presence and comparison, and adds nothing on counting: both models are level with always saying "0". This is a known weakness of templated benchmarks, not of your implementation — but it is the honest floor to judge the models against, and an examiner may well ask. The dashboard shows it as a grey bar, and ml/scripts/question_only_baseline.py reproduces it in one command.

The first cross-attention attempt — the story to tell

What happened: the first run scored 36.06% overall (27.07% average), with rural/urban and counting both at exactly zero. Its validation accuracy sat on the same one or two values from epoch 0 to epoch 9 and the training loss never moved. That is the signature of a model giving nearly the same answer whatever it's asked.

The cause: a design bug of mine. I had squashed the image and the question to one vector each before the attention step, so attention ran over a single item — and softmax over one item is always exactly 1. The question had zero influence on the output. I proved it: changing the question changed the output by exactly 0.0, while changing the image changed it by 0.84.

The fix: keep both as sequences, so every question word attends over all image patches. Retrained: 36% → 72%. I also made the model choose its fusion in one place (three scripts had each swapped it in by hand, which is how it went unnoticed) and added an automated test that both the question and the image must change a fusion module's output.

Why tell it: a run that finishes without errors isn't proof the model works. Finding, proving and fixing this from a flat training curve shows you understand the model, not just the tooling.

07 — Do this on stage

Live demo script

Every question below was run through both models on this machine. The demo leads with the one kind of question where the image, not the wording, decides the answer.

Ten minutes before

  1. Plug in; close heavy programs (the models run on the CPU). Be on the internet for the map.
  2. In PowerShell, from the project folder, run .\scripts\dev.ps1 demo. Wait for the sign-in page, sign in, and check the top-right says "2 of 2 models online".
  3. Have three files ready from ml/dataset/rsvqa_lr/images/Images_LR/: 237.tif (urban), 246.tif (rural), 315.tif (farmland). All are from the held-out test set. Spare: 235.tif (rural). Do not use 243.tif — re-verified 2026-09-24, the two widened models now disagree on it (elementwise: urban 71%; cross-attention: rural 59%). Genuinely interesting if it comes up in conversation, but not what you want for this opening beat.

The walkthrough (about 6 minutes)

  1. What it is (30 s). "Upload a satellite image, ask a question in plain English, and two small models answer side by side — one uses simple fusion, the other cross-attention. Both are trained on two datasets together, not just one, so they generalise beyond a single benchmark."
  2. Upload (30 s). Drag in 237.tif. Point at the metadata: size, resolution, coordinate system, location. "It reads the GeoTIFF's own geo information, so the image knows where on Earth it is."
  3. Urban vs. rural (2 min). Open 237, click the chip "Is it a rural or an urban area?" → both say urban (99% / 79%). Upload 246, same question → both say rural (100% / 99%). "Same question, two images, two answers — it's reading the picture, not just the words."

09 — The "why," not just the "what"

Why this plan, and why these specific choices

A guide asking "why" is testing whether you understand the decisions or just followed a tutorial. Each of these has a one-line reason — lead with that, then expand only if asked.

Why the plan changed at all

Say this one plainly, it reflects well on you: the original plan called an existing vision-language model through an API and built a verification layer on top of it. Your guide reviewed that and said the model itself — training one and understanding its internals — is the actual point of the project, not the web app around it. The plan changed because that's the right call, not because the earlier work was wasted: the web app became the delivery layer for the trained model.

Why LiT-4-RSVQA specifically

Because it directly answers "can a model this small still be accurate?" — and the paper's own results say yes: 8.1M parameters beating a 277M-parameter baseline by roughly 9 accuracy points, and pretrained-then-fine-tuned beating training-from-scratch by nearly 13 points on the identical architecture. That second number is the reason this project fine-tunes pretrained encoders. It's also realistic for a semester on a shared GPU slice, which a multi-billion-parameter model is not.

Why RSVQA-LR, and not a bigger benchmark

Small enough to fully train and evaluate in the time and compute available, and it's the benchmark the paper itself reports on. Richer benchmarks now exist (see §11); moving to one is honest future work, not something overlooked.

What the original contribution is

The paper's design is the baseline, reproduced. The experiment is swapping its elementwise fusion for cross-attention on identical data, encoders and training settings, so any difference is attributable to that one change. The result was a tie — a clean negative result, reported as one.

Why a layered architecture in the web app

Four layers — domain rules, use cases, infrastructure, API — with inner layers forbidden from depending on outer ones, enforced by a test that fails the build. That's why the database can swap from SQLite to PostgreSQL, or the model runner can change, without touching business logic.

Why widen the training to a second dataset

The robustness study (§06, §02 Step 11) turned "it might be brittle" into a measured fact: dimming an image alone dropped rural/urban accuracy from 92% to 62% — close to the level of ignoring the image entirely. A model that only works on a small set of selected images from one dataset isn't a strong result, whatever its accuracy number says. Retraining on a second, independently-collected dataset (RSVQA-HR) with augmentation directly targets that: it can't fix everything (half-resolution robustness only improved for one of the two fusions), but it turned a real weakness into a measured, mostly-fixed one, and it's the difference between "works on this benchmark" and "works on satellite imagery like this benchmark's."

Why training ran on the institute HPC

No GPU on the laptop, and CPU training is impractical at this size. The cluster is used through SLURM after a formal declaration form. Everything was written and CPU-verified first so GPU time went to running working jobs. The real cluster still surfaced four problems no laptop could have (the reserved-GPU labelling, a driver/CUDA mismatch and a GPU-slice addressing problem that each made training silently fall back to the CPU, and an out-of-memory error), each diagnosed from the cluster's own output.

10 — For "do you actually understand VQA"

The VQA background

Visual Question Answering: a model is given an image and a question in natural language, and must produce an answer grounded in the image. This project frames it as classification — picking the right answer from the 1,000 most frequent in the training set — rather than generating free text. That's a standard framing in this literature, exactly how the original RSVQA benchmark and LiT-4-RSVQA both work, and it's why the app can't answer open-ended "describe this" questions.

The part worth being able to say clearly: satellite VQA is not just "VQA on different photos." It's a different problem, for four concrete reasons.

11 — Name these with confidence

Papers and datasets worth knowing cold

The core reading is the two surveys originally assigned — Vision-Language Modeling Meets Remote Sensing (Weng, Pang & Xia, IEEE GRSM, Sept 2025) and Visual Question Answering: A Survey of Methods, Datasets, Evaluation, and Challenges (Kim et al., ACM Computing Surveys, May 2025) — plus the paper this project's architecture follows, and a literature search covering 2024–2026.

LiT-4-RSVQAHackel, Clasen, Ravanbakhsh & Demir — TU Berlin, 2023 (arXiv:2306.00758) — the paper this project follows

BERT-Tiny text encoder, a lightweight pretrained image transformer (XCiT-Nano, DeiT-Tiny or MobileViT-S), elementwise-product fusion, MLP classifier. Best result — 64.61% average accuracy at 8.1M parameters, beating a 277M-parameter baseline by about 9 points. Its most important number for this project: the same architecture trained from scratch scores only 51.71% — nearly 13 points lower. That's the evidence behind fine-tuning rather than training from zero.

RSVQALobry, Marcos, Murray & Tuia — IEEE TGRS, Dec 2020

The founding benchmark this project trains and evaluates on (the low-resolution split, RSVQA-LR). ResNet-152 + skip-thought vectors, elementwise fusion — the direct ancestor LiT-4-RSVQA is a lightweight successor to.

GeoChatKuckreja et al. — CVPR 2024

Useful as contrast, not as a target: CLIP ViT-L/14 → MLP connector → Vicuna-v1.5-7B, fine-tuned with LoRA. Billions of parameters, generates free text rather than classifying. The honest answer to "why not build this" is scale — and that it isn't the depth-of-understanding exercise your guide asked for.

What's moved since 2023 — from a literature search run September 2026

The biggest systems keep getting bigger: RS-MoE (Lin et al., 2024) routes between expert LLMs; Co-LLaVA (Liu et al., 2025) combines two VLMs and beats GeoChat on RSVQA-LR itself; HSF-Net (Liu et al., 2026) adds hierarchical semantic fusion on top of LLaVA. All are billion-parameter systems — good to name for currency, not to chase.

One number that backs this project's premise: RS-MoE's 1B-parameter variant performs comparably to 13B-parameter VLMs — current, independent evidence that a small, efficient model can compete with much larger ones.

On benchmarks: EarthVQANet (Wang et al., 2024) describes RSVQA as covering "basic statistics for general objects," and the much larger RSVLM-QA (Zi et al., 2025 — 162,373 pairs vs. RSVQA-LR's 77,232) has since appeared. This project's scope is intentionally the simpler, established benchmark; richer ones are future work.

MQVQA (Zhang et al., 2023) is directly comparable prior work — a multi-step attention mechanism on the same benchmark family. And Lu et al.'s 2023 review of attention in VQA fusion is the citation for why testing cross-attention against the elementwise baseline is a literature-grounded experiment.

12 — Say these in plain words

Glossary

Each one is a definition you could say to a friend.

VQA (visual question answering)
Give a computer a picture and a question in ordinary language; it answers in ordinary language.
Parameter
One of the adjustable numbers inside a model. Learning means adjusting them. This model has about 8 million; large models have billions.
Vector
A list of numbers. Models turn pictures and words into vectors so they can compare and combine them.
Encoder
The part that turns raw input (an image or a sentence) into vectors the rest of the model can use.
Transformer
A kind of model built around "attention" — letting every piece of the input look at every other piece to decide what matters. XCiT-Nano and BERT-Tiny are both small transformers.
Patch / token
A small piece of the input: a 16 × 16 square of the image, or a word piece of the question.
Pretrained / fine-tuned
Pretrained: already taught general skills on other data (ImageNet photos, general text). Fine-tuned: then adjusted on this project's data. The paper found this beats starting from scratch by about 13 points.
Fusion
The step that combines what the image says with what the question asks.
Elementwise product
Multiplying two equal-length lists of numbers position by position. The simple fusion in the paper and in the baseline.
Attention / cross-attention
Attention: scoring how relevant each piece is, then taking a weighted mix. Cross-attention: the question's words score the image's patches, so each word pulls in the regions relevant to it.
Softmax / confidence
Softmax turns raw scores into probabilities that add to 100%. The top one is the "confidence". A high confidence is not a guarantee of being right.
Classification framing
Treating the answer as a choice from a fixed list (here, the 1,000 most common answers) instead of writing free text.
Loss (cross-entropy)
A single number for how wrong the model's guesses are. Training tries to make it smaller.
Epoch / batch
An epoch is one full pass over the training data. A batch is the handful of examples (64 here) processed before each adjustment.
Learning rate / AdamW
The learning rate is how big each adjustment is. AdamW is the standard method for deciding the adjustments.
Train / validation / test
Train: what it learns from. Validation: checked during training to spot memorising. Test: kept untouched until the end for the honest score.
Overfitting
Doing better on the training data while not improving (or getting worse) on new data — memorising instead of learning.
Overall vs. average accuracy
Overall: the plain share of questions answered correctly. Average: the mean of the four per-type accuracies, matching the paper. A small type like rural/urban (100 questions) has the same weight as a huge one.
Baseline
The reference you compare against. Here: the paper's design (elementwise fusion), and separately a "no image" guess.
Ablation / controlled experiment
Change one thing, keep everything else identical, see what moves. Swapping only the fusion is the project's experiment.
Language bias / no-image baseline
When the wording of a question already predicts the answer. A predictor that never sees the image and answers by wording alone scores 70.4% here.
Checkpoint
A saved snapshot of all the model's numbers. The app loads two of them.
HPC / SLURM / MIG
HPC: the institute's shared GPU cluster. SLURM: the scheduler you submit jobs to. MIG: splitting one big GPU into several smaller, separate slices.
GeoTIFF / CRS / GSD
GeoTIFF: an image file that also stores where on Earth it is. CRS: the coordinate system used (these files use Web Mercator). GSD: how much ground one pixel covers.
13 — Rehearse these out loud once

Questions to expect, and how to answer them

The four everyone asks. These are the questions a random visitor at your stall is just as likely to ask as Ashish — say them in plain words first, and only go technical (the jargon versions further down this section) if they specifically ask for more depth.

"Why are there two models, not one?"

Because comparing two ways of doing the same thing is the actual experiment I ran — it's the one part of this project that's genuinely mine, not just reproduced from a paper. Model A combines the picture and the question in a simple way. Model B combines them in a fancier way, where the question can "look around" the whole picture before deciding on an answer. Everything else about them is identical, so any difference in how well they do is because of that one change — not because of anything else. With only one model, I'd have nothing to compare and nothing to say "why" about. The honest result: the fancier way didn't actually do any better here — which is itself a real, useful finding, not a failure.

"Why can't I just type any question I want?"

Because this isn't a chatbot that writes sentences — it's a model that picks the best answer from a list of the 1,000 answers it learned during training, like a multiple-choice test instead of an essay question. A model that could freely write any sentence needs to be enormously bigger — billions of adjustable settings instead of about 8 million — and would need far more computing power and training data than a student project on a shared university GPU realistically has. Picking from a fixed list is what lets a model this small actually work well, and it's the same approach the published research this project follows uses. You can still type a question in your own words — the model does its best to match it to what it learned — but it works best on the plain, direct style of question it was actually trained on: "Is there a road?", "How many buildings are there?", "Is this a rural or an urban area?"

"Why does it only work on certain images?"

Because it only ever learned what roads, buildings, farmland and so on look like from two specific kinds of pictures: satellite images of the Netherlands, and aerial photos of a few American cities, both taken looking straight down from above. If you show it something that looks very different from those — a close-up ground-level photo, or a satellite image at a very different zoom level — it still gives an answer (it always picks something), but that answer becomes unreliable, sometimes confidently wrong. This is a completely normal limitation for this kind of model, not a bug, and I measured it directly and fixed part of it by training on a second, very different dataset — see the next answer.

"So what kind of images does it actually work well on?"

Pictures taken looking straight down — like a satellite or drone photo, not a street-level photo — showing a stretch of land a few kilometres across, at roughly the same zoom level as Google Maps' satellite view or a bit sharper. It's been trained and tested on real imagery like this from the Netherlands and several American cities, including one city, Philadelphia, that it had never seen before, specifically to check it wasn't just memorising one place. Ground-level photos, radar images, or pictures zoomed in far closer or wider than that are outside what it was trained on, and I'd expect it to need retraining to handle those properly — I'd say that plainly rather than guess if asked.

"Did cross-attention beat the baseline?"

No — it tied it, both before and after I widened the training data. Most recently: 71.96% against 72.02% overall on 9,838 held-out questions. Each model was trained once, so the honest conclusion is that the richer fusion didn't measurably help here, at about 13% more parameters — and that held up across two completely different training setups, which makes it a more robust negative result than a single comparison would be. Repeating runs with different seeds would be the next step.

"Your first cross-attention run scored 36%. What happened?"

A bug in my own design. I'd reduced the image and the question to one vector each before attention, so it attended over a single item and softmax gave it a weight of exactly 1 — the question never reached the classifier. I spotted it from a training curve that never moved, proved it by showing the output changed by exactly zero when I changed the question, and fixed it by attending over all image patches. Retraining took it from 36% to 72%, and there's now a test that guards against it. Lead with what you noticed and how you proved it — the flat curve, the zero — not with the fact that it went wrong.

"Why is your accuracy higher than the paper's 64.6%?"

It isn't a fair comparison, and I don't claim it is. The paper trained on a much larger dataset (RSVQAxBEN, about 15 million examples) and reports on that setting; I trained and tested directly on RSVQA-LR. The number that matters is that my reproduction of their architecture works, and that the parameter count matches (8.2M vs. their 8.1M).

"Why not just fine-tune or call an existing model like GeoChat or Qwen2.5-VL?"

Two reasons. Scale: those are billion-parameter systems that need far more compute than a shared institute GPU realistically provides in a semester. And you were asked to understand a VQA model's internals, not call an API. A model this size can be trained, tested, debugged and fully explained end to end by one person; a 7B-parameter model can't, at this depth.

"You're following a published paper's architecture. What's actually yours?"

The paper's architecture is the baseline, reproduced honestly. The original piece is the cross-attention experiment on top — implemented, debugged, trained and measured against the paper's own baseline on identical data and encoders. I also built the pipeline, the training and evaluation code, the model-serving backend and the interface, and I can explain every component. Using pretrained weights isn't a shortcut around "making your own model" — it's how the field works, and the paper's own numbers show why.

"Why does a satellite VQA tool need authentication and admin roles?"

It was built under the original plan, and it turned out to be the right foundation: uploaded images and question history belong to a user, so the model service needs to know whose data it's touching. It has 111 tests and real security properties — Argon2id hashing, single-use refresh tokens, role-based access.

"You don't have a GPU. How did training happen?"

On the institute's HPC cluster through SLURM, after the formal declaration form. Every script was verified on CPU first so the GPU time ran working jobs. Even so, the real cluster exposed four problems no laptop could — the reserved-GPU labelling, a driver/CUDA mismatch and a GPU-slice addressing problem that each silently fell back to the CPU, and an out-of-memory error — each diagnosed from the cluster's own output.

"What happened to the SGV / spectral-verification idea from the original plan?"

Set aside when the priority moved to the model itself — checking a model's quantitative claims against spectral measurements doesn't apply the same way to a classifier that picks from a fixed answer list. Whether it returns as a layer later is genuinely open: an idea on hold, not one proven wrong. A guide respects an owned pivot far more than one glossed over — say plainly that the plan changed and why.

"What are the limits?"

It answers from a fixed list of 1,000 answers, so it can't write free text or answer questions outside that vocabulary. Counting is weak (about 28%). It now generalises across two datasets and an unseen city, but that's still Sentinel-2 and 15cm aerial imagery specifically — an unfamiliar sensor or a resolution far outside that range would likely need fine-tuning. Half-resolution robustness only improved for one of the two fusions, and scale sensitivity (a heavily zoomed crop) isn't fully solved. Each model was trained once. And the test sets are narrower than newer benchmarks like RSVLM-QA.

"Walk me through what you did, from the start."

Use §02: plan, review, pivot, build, cluster, baseline, serving, the failure, the fix, the app, the honest tests, backup, and widening. Thirty seconds is: "I started with a big-model plan, my guide asked for a model I train myself, so I rebuilt it around a small published design, trained a baseline on the cluster, tested my own cross-attention idea — which failed at first because of a bug I traced and fixed — built a working demo, measured where it broke, then retrained both models on a second, independent dataset with augmentation, which fixed the robustness weakness and proved they generalise to a city neither ever saw."

"How much of that accuracy is just guessing from the question?"

A lot of it, and I measured it. A predictor that never sees the image and answers with the most common training answer to each exact question scores 70.4% overall on the test set; my models score 72.0% and 72.0%. So the image adds about a point and a half overall. It clearly matters for rural/urban — 56% without the image, 88% and 89% with it — helps a little on presence and comparison, and doesn't help counting at all. That's a known weakness of templated benchmarks like RSVQA, and it's why I show the no-image bar next to the models on the dashboard. Lead with it before you're asked. It turns the strongest objection into evidence that you evaluated the result.

"Why classification instead of generating a sentence?"

It's the standard framing for this benchmark and it's what the paper does. It makes accuracy exactly measurable, keeps the model small, and is honest about scope: the model picks from the 1,000 most common answers. The cost is that it can't answer open-ended questions, which I say up front.

"Why BERT-Tiny and XCiT-Nano?"

They're the paper's best small combination: BERT-Tiny is 2 layers and 128 numbers wide, XCiT-Nano is a small pretrained image transformer, and together the model is about 8 million parameters. Small enough to train in about an hour on one GPU slice and to run on a laptop CPU, which matters for a live demo.

"Explain cross-attention in one breath."

"Every word of the question looks across all the little squares of the image, scores how relevant each is to that word, and pulls in a weighted mix of them — so 'road' can focus on road-looking patches — instead of the image and the question each being squashed into one summary and multiplied."

"How do you know it isn't just memorising the training data?"

Two checks. Validation accuracy was scored after every epoch on data it wasn't training on, and the final score is on a separate test set used once. The baseline's training loss fell from 1.42 to 0.91 over ten epochs while validation accuracy stayed at about 73–74% — so after the first epoch it was mostly fitting the training set better, not generalising better, which is why I didn't run longer.

"Did you pick the best epoch using the test set?"

No. I evaluated the final epoch, once, on the test split. The validation set was only for watching training.

"Why batch 64, learning rate 5e-4, and why the epoch count changed from 10 to 8?"

The learning rate is the paper's. The paper used batch 512, which ran out of memory on the roughly 10 GB GPU slice I had, so I used 64 — for every model, original and widened. Ten epochs was the original single-dataset setting; once RSVQA-HR was mixed in, each epoch covers far more data (RSVQA-LR's full training set plus 60,000 sampled RSVQA-HR questions), so 8 epochs was enough, chosen by watching validation accuracy plateau the same way it did originally. I didn't otherwise tune anything, and both fusions always use identical settings, which keeps the comparison fair.

"Which number should I quote — overall or average?"

Overall means "how often is it right" — 72.0% for the currently-deployed elementwise model. Average is the mean of the four question types, which is what the paper reports, so use it when comparing to the paper. It's less stable here because rural/urban has only 100 questions but counts as a quarter.

"The app says about 16 m per pixel but Sentinel-2 is 10 m. Which is it?"

Sentinel-2's native resolution here is about 10 m. The files are stored in Web Mercator, which stretches distances away from the equator by 1/cos(latitude), and at 51–53°N that turns 10 m into roughly 16–17 m — the app reports 15.8 m at 51.2°N and 16.5 m at 52.8°N, which matches. Say it as "the map projection stretches it", not as a data problem.

"Would it work on other cities or other satellites?"

Partly tested now, and the answer is genuinely encouraging. I retrained on a second, independent dataset (RSVQA-HR — 15cm aerial imagery, a different sensor and scale from RSVQA-LR's 10m Sentinel-2) and evaluated on Philadelphia, a city that appears nowhere in training in any form. It still answers about three-quarters of questions correctly there — a real ~5-point gap from RSVQA-HR's own test cities, not a collapse. That's the actual evidence for "generalises beyond a handful of selected images." What's still untested: a sensor or region unlike either training dataset, or resolutions far outside the ~10–15cm/pixel range these were trained on — I'd still expect those to need fine-tuning, and I'd say so plainly.

"Why does dimming an image break the model, and did you actually fix it?"

A model trained on one dataset learns shortcuts specific to that dataset's exact appearance, not the underlying scene — so a change that doesn't touch the true answer (brightness, resolution) can still flip the prediction. I measured it directly: dimming an image alone dropped rural/urban accuracy from 92% to 62% on the original model. After retraining on a second dataset with augmentation that includes brightness and resolution changes, the same test now costs 0 points for elementwise fusion and 3 for cross-attention — essentially fixed for the exact weakness the study found. Half the story is honest, though: a 2× zoom crop still hurts accuracy meaningfully, so scale sensitivity isn't fully solved, and I say that rather than claim a complete fix.

"Did you use AI tools to build this?"

Answer truthfully and within your institute's rules. If it's accurate for you: "Yes — I used an AI coding assistant for implementation. I made the decisions — the pivot, the model choice, the cross-attention experiment, reporting the tie honestly — and I can explain, run and reproduce every part; I found and diagnosed the cross-attention bug from the training curve." Then prove it by explaining something. Never claim to have hand-written what you didn't.

"What would you do next?"

Repeat each run with several random seeds to measure run-to-run noise; move to a larger benchmark such as RSVLM-QA; visualise which patches each word attends to, to see if cross-attention learns something sensible; try to fix counting, which is stuck at the no-image level; close the remaining scale/zoom sensitivity that the widened training didn't fully fix; and compare against a larger model to put a number on the small-model trade-off.

15 — The most important paragraph on this page

If you're asked something you genuinely don't know

Say so, specifically. "I haven't tested that — I'd need to run it on the held-out set" is a completely credible answer, and far safer than guessing and being caught on a follow-up. The one thing to avoid is a vague deflection ("yeah, that's mostly done") that invites exactly the follow-up you can't answer. A precise "not tested, here's how I would" reads as someone in control of their own scope — and this project has the results and the honest edges to back that up.
